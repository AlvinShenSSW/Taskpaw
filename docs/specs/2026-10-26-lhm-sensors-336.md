# #336 — Sensors: CPU/GPU temperature and fan RPM from a resident LibreHardwareMonitor

Date: 2026-10-26 · Base: `cb9aca4` (main, 3.10.6) · Branch: `afk/lhm-sensors-336`
Planner: Claude (driver). Implementer: Claude Opus 5.5. Gate: Codex astra xhigh.
Design v2 (after critic round 1; see Debate record).

## Spec review

3.10.4–3.10.6 (#323) ship GPU temperature only, through a dedicated
`core/temperatures.py` sampler (its own thread and its own `nvidia-smi` process
every 5 s, next to the shared `gpu_sample` query that already runs every 4 s),
nine reason codes, a 45-line validator in `core/power_fleet.py`, and three
layers of age/stale arithmetic (agent `age_s`, fleet `+elapsed`, UI
`temperatureView.ts` max-with-previous). The UI strip renders GPU only.

Operator decision (2026-10-26): CPU and GPU temperature plus fan RPM, read from a
resident LibreHardwareMonitor (LHM) on each machine; **no chassis or board
temperature**; no configuration; replace the #323 chain rather than extend it.

Facts verified by the planner on 2026-10-26: LHM 0.9.6 serves
`GET /metrics` (Prometheus text) from its Remote Web Server; lines look like
`lhm_cpu_temperature_celsius{sensorName="CPU Package",hardwareName="...",sensorId="...",...} 45`;
metric names are `lhm_<hardwaretype>_<sensortype>_<unit>` with `celsius` for
temperatures and `rpm` for fans; the WMI provider was removed with the .NET 10
build. `nvidia-smi` exposes fan speed only as a percentage, so fan RPM comes from
LHM only. On the controller (Minisforum MS-02 Ultra, EC-controlled fans) whether
LHM exposes fan RPM is unverified; on the GPU workers (desktop boards) it is
expected. The exact spelling of the hardware-type segment and whether
sub-hardware (SuperIO fans under Motherboard) is exported are unverified until
the operator's Step 0 dump, so nothing in the design depends on them.

Core need: one sensor line per machine on the 功耗 page, from one provider, with
the smallest possible chain.

## Acceptance criteria

- AC1 `taskpaw_v3/core/sensors.py` replaces `core/temperatures.py`. A
  `SensorSampler` thread samples every 5 s: `GET http://127.0.0.1:8085/metrics`
  (urllib, 2 s timeout, no auth, fixed address). One regex over the lines
  yields `cpu_c` (the `temperature_celsius` sample whose `sensorName` equals
  the constant `CPU_SENSOR = "CPU Package"`, whatever the hardware type),
  `gpu_c` (max of the `temperature_celsius` samples named
  `GPU_SENSOR = "GPU Core"`), `fans` (every `fan_rpm` sample with a finite
  value > 0 as `{"name": sensorName, "rpm": int}`, LHM's name verbatim, order
  as served). Selection never depends on the hardware-type segment of the
  metric name (critic C6). Non-finite values (`NaN`, `+Inf`) are dropped
  everywhere: a non-finite temperature is `null`, a non-finite fan is skipped,
  so nothing non-finite ever reaches a JSON response. Temperatures are
  rounded to one decimal.
- AC2 Without LHM (connection refused, timeout, non-200, unparsable body):
  `source` is `"nvidia-smi"` when `gpu_sample()` has a temperature, else
  `null`; `cpu_c` null, `fans` empty. `temperature.gpu` is added to
  `gpu_sample.QUERY`; `parse` keeps the max as `temp_c` (`None` when every GPU
  reports `[N/A]`). No second `nvidia-smi` process anywhere.
- AC3 `snapshot()` returns `{"at": <wall seconds>, "source": "lhm" | "nvidia-smi" | null, "cpu_c", "gpu_c", "fans"}`
  with `at` the wall time of the last completed sample (null before the
  first); the sampler also keeps the monotonic time of that sample for AC4.
  No age, stale, reason or label fields in the snapshot.
- AC4 The agent `/status` carries `sensors` (the key `temperatures` is gone).
  The fleet stores a peer's `sensors` object as received and `sensors_mono` =
  the controller's monotonic clock at receipt; the power view's rows (peers
  and the local machine) expose `sensors` and `sensors_age_s` = seconds since
  that receipt (local: since the sampler's last sample), computed with the
  controller's monotonic clock at request time; `null` when never received.
  No wall clock crosses a machine boundary and the browser never compares
  wall clocks (critic C3). `_temperatures`, `_aged_temperatures`,
  `_thermal_number` and the `temperature_*` entry fields (including the
  `temperature_status_ok=False` writes in `_refresh` and `temperature_mono`)
  are deleted; a peer that stops answering keeps its last `sensors` and ages
  out; duplicate/self peer rows keep showing their own `sensors` as today
  (critic C4).
- AC5 UI: `TemperatureStrip.tsx` and `temperatureView.ts` are replaced by
  `SensorLine.tsx` rendering the confirmed V3 preview: `CPU 68 °C · GPU 40 °C ·
  风扇 CPU Fan 1218 / SYS Fan1 2554 RPM · LHM · 4 秒前`; items without a value
  are not rendered; `source` null with no GPU reading → `CPU / 风扇：LHM 未运行`
  next to whatever is present; no `sensors` key → `传感器未提供 · 需升级 TaskPaw`;
  age > 30 s → the line turns amber with `已过期 · 最后读数 N 秒前`; connection
  lost (`failed`) is shown through the same stale path. The age shown is
  `sensors_age_s` plus the seconds since the browser received the response:
  `PowerPage.tsx` keeps the request-relative receipt stamp it has today
  (`performance.now()` at resolve, the `temperatureReceivedMs` pattern, renamed
  `sensorsReceivedMs`) and the existing `nowMs` ticker; no `Date.now()` is
  compared with a controller clock (critic C3).
- AC6 `api.ts`: `MachineSensors { at: number | null; source: "lhm" | "nvidia-smi" | null; cpu_c: number | null; gpu_c: number | null; fans: { name: string; rpm: number }[] }`;
  `PowerView.sensors`, `PowerView.sensors_age_s`, `PowerPeerRow.sensors`,
  `PowerPeerRow.sensors_age_s`; `MachineTemperatures` and `TemperatureSensor`
  are removed, including the never-populated `WorkerCurrent.temperatures`
  field at `api.ts:212` (critic C2). The machine-row mapping lives in
  `powerView.ts` (`Machine.temperatures` at ~27, `peerMachine` ~80,
  `machinesOf` ~95), not `powerModel.ts` (critic C2).
- AC7 Tests: `taskpaw_v3/tests/conftest.py` lines 84-93 (the autouse
  `_temperature_isolation` fixture that imports `core.temperatures` and
  patches `_gpu_reader`) becomes an autouse fixture that patches
  `sensors.read_sensors` to return a fixed all-null stub, so no test reaches
  `127.0.0.1:8085` or a real `nvidia-smi` through the sampler (critic C1);
  `test_temperatures.py` and `test_temperature_fleet.py` are deleted;
  `test_power.py` line ~180 (exact `gpu_sample` dict equality) gains `temp_c`
  (critic C5); `test_sensors.py` covers the parser on a fixture `/metrics`
  text (CPU, two GPUs, four fans, a zero-RPM fan and a `NaN` sample dropped,
  `# HELP`/`# TYPE` lines and a trailing timestamp ignored), the no-LHM path
  through a patched `gpu_sample`, the sampler's snapshot before/after a sample
  and its stop; `test_power_fleet.py` covers `sensors` passthrough with
  `sensors_age_s` and an old agent without the key; `test_launcher.py`'s
  temperature case (~95-180, which injects `reader=`) is rewritten for
  `sensors`; `gpu_sample` tests cover `temp_c`; UI `sensors.test.tsx`
  (replacing `temperatures.test.tsx`) covers the five states of the preview.
  Full suite, UI tests, lint, mypy green.
- AC8a Backend and UI land as **one unit** on the branch: a backend-only
  commit would leave the old strip reading a missing key and show
  "温度未提供" for every machine (critic C5). Until the UI part is confirmed and
  built, the branch is not local-complete and the issue stays `OUTSTANDING`.
- AC8 `docs/guides/deployment.md` gains a short "传感器（可选）" section: install
  LHM, run as administrator, install PawnIO when prompted, Options: Run on
  Windows startup / Start minimized / Minimize to tray, Remote Web Server: Run,
  port 8085, listen on 127.0.0.1; TaskPaw reads it automatically, nothing to
  configure. CHANGELOG entry. **No version bump in this issue**: the stack is
  released once at the end of the run; a mixed fleet keeps working because
  `sensors` is optional and an old agent shows 需升级.

## Frozen issue contract

- Invariants kept: the shared `gpu_sample` cache semantics (4 s, one lock;
  consumers read by key, `parse` tolerates row width); `/status` and the power
  view keep every other field; the fleet's power and energy paths are
  untouched; no settings field, no agent.yaml key, no new config; one sampler
  thread as before (replacing, not adding); the launcher keeps the same
  module-attribute constructor, `start()` and `stop() -> bool` hooks.
- Allowed user-visible change: the sensor line shows CPU and GPU temperature
  and fan RPM; wording per the preview; old agents show 需升级 TaskPaw.
- Non-goals: board/chassis temperature, HWiNFO, embedding
  LibreHardwareMonitorLib, fan control, history, alerts, a provider setting,
  per-GPU breakdown, any wall-clock comparison across machines.
- Causal boundary: `core/sensors.py` (new), `core/temperatures.py` (deleted),
  `core/gpu_sample.py` (one field), `core/power_fleet.py` (passthrough instead
  of validation), `agent/server/launcher.py` (wiring), `tests/conftest.py`
  (fixture swap), the UI files named in AC5/AC6 (`SensorLine.tsx`,
  `PowerPage.tsx`, `powerView.ts`, `powerStyles.ts`, `api.ts`), tests, the
  guide, CHANGELOG.

## Assumptions

- A1 **Step 0 pending (operator).** `CPU Package` is LHM's standard name for
  Intel package temperature (AMD reports `Core (Tctl/Tdie)`); `GPU Core` for
  NVIDIA (`GPU Hot Spot` and `GPU Memory Junction` exist and are deliberately
  not used). The operator's `/metrics` dump from the controller and one worker
  may rename the pinned constants; they are the single point of change.
- A2 LHM's Prometheus endpoint emits one sample line per sensor with the
  `sensorName` label; verified by reading `HttpServer.cs` (v0.9.6), not by a
  live fetch (LHM is not installed on the development machine). A `}` inside
  a label value would break the line regex; accepted as rare.
- A3 `nvidia-smi --query-gpu=...,temperature.gpu` returns an integer °C or
  `[N/A]` (checked on this machine: `0, 40, 1, 1763, 8151, 12.23`); the
  existing `_number` helper handles `[N/A]`.
- A4 **UI preview confirmation pending (operator).** The V3 preview (linked in
  #336) was published and a layout fix applied after the operator's remark;
  explicit confirmation has not been given. The backend may be built and
  reviewed first, but per AC8a the branch is complete only with the UI.

## Approach

`core/sensors.py` (~120 lines):

```python
LHM_URL = "http://127.0.0.1:8085/metrics"
CPU_SENSOR, GPU_SENSOR = "CPU Package", "GPU Core"
_LINE = re.compile(r'^lhm_[a-z0-9_]+_(?P<kind>temperature_celsius|fan_rpm)\{(?P<labels>[^}]*)\}\s+(?P<value>\S+)')
_NAME = re.compile(r'sensorName="((?:[^"\\]|\\.)*)"')

def parse_metrics(text) -> dict:  # cpu_c, gpu_c, fans from the LHM body; non-finite dropped
def read_lhm() -> dict | None:    # urlopen(LHM_URL, timeout=2); None on any failure
def read_sensors() -> dict:       # LHM, else gpu_sample() temp_c as nvidia-smi, else nulls

class SensorSampler:
    # same test seams as the old sampler: reader=, clock=, wall=, interval=
    # start() / stop(timeout=9.0) -> bool / tick() / snapshot(); keeps `_mono`
    # (monotonic time of the last completed sample) for sensors_age_s.
    # tick() resolves the module attribute at call time, `(self._reader or
    # read_sensors)()`, exactly as temperatures.py:166 does today, so the
    # conftest autouse patch of `sensors.read_sensors` takes effect; the
    # no-LHM test in test_sensors.py binds the real function at import.
```

`gpu_sample.QUERY` becomes exactly
`"utilization.gpu,memory.used,memory.total,power.draw,temperature.gpu"`; `parse`
reads the temperature from `parts[4]` (the planner's six-column sample in A3
came from a different query; the column order here is the one that counts).

`power_fleet.py`: in `_refresh`, `sensors=status.get("sensors") if isinstance(..., dict) else None, sensors_mono=self._clock()` on a successful status; failure branches no longer touch sensor fields; in the snapshot row, `"sensors": entry.get("sensors")` and `"sensors_age_s": now - mono if (mono := entry.get("sensors_mono")) is not None else None` (`_new_entry` has no such key, so a never-answered peer yields null).

`launcher.py`: `sensors.SensorSampler()` in place of the temperature sampler
(same module attribute so `test_launcher.py` can monkeypatch it; `start()` at
the same place; `stop()` with its 9 s default, above the 7 s worst-case tick
of 2 s urlopen + 5 s nvidia-smi, same "did not stop in time" log; critic C7);
`"sensors": sampler.snapshot()` in `/status`; in the power view `"sensors"`
plus `"sensors_age_s"` for the local machine from the sampler's monotonic
stamp.

UI: `SensorLine.tsx` (≈40 lines) per the preview; `PowerPage.tsx` keeps a
request-relative receipt stamp (`sensorsReceivedMs = performance.now()` set
inline in its `readDay` query function, replacing the call into
`stampPowerTemperatures`; the max-with-previous logic is dropped) and the
`nowMs` ticker, and passes `m.sensors`, `m.sensors_age_s`, the seconds since
receipt and `failed`; `stampPowerTemperatures`/`TimedPowerView`/
`temperatureView.ts` go away; `powerView.ts` maps `sensors`/`sensors_age_s`
onto the machine rows the way it maps `temperatures` today.

Alternative rejected: keeping `temperatures.py` and adding LHM beside it (two
samplers, two key sets, the three-layer age arithmetic stays).

## Key implementation notes

- Keep `read_lhm` to one `urlopen` with `timeout=2` and a `read()`; any
  exception → `None`. No retries, no backoff, no reason codes.
- `fans`: skip samples whose value is not finite or ≤ 0; names come from
  `sensorName` with Prometheus label escapes (`\"`, `\\`, `\n`) unescaped.
  GPU and pump fans that LHM reports are listed like any other fan.
- `gpu_sample.parse`: a fifth column; keep the existing three-column tolerance.
- The UI shows integers (`Math.round`) as in the preview.
- Do not add a settings entry, an env override or a hostname option.
