# 阶段 2 待实机清单（交给操作者 / T09 补充）

阶段 2 的代码（多机调度、传输、失联处理、4K 修复）只在临时目录、假工具和假 GPU 上验证过。下面这些只有在你的真实环境里才能确认。
对应合同：[2026-10-24-media-workflow-p2-5-4k-docs.md](2026-10-24-media-workflow-p2-5-4k-docs.md)（R7）。阶段 1 的清单见
[2026-10-20-media-workflow-phase1-real-machine-checklist.md](2026-10-20-media-workflow-phase1-real-machine-checklist.md)。

首次安装、向导、防火墙 UAC、立即重启、令牌与地址自愈等「零配置」项，请直接按
[#299 零配置实机清单](2026-10-23-zero-config-setup-299-real-machine-checklist.md) 逐条做，这里不重复。

## 准备

1. 五台机器都装同一个构建（主控 5060 8 GB、四台 GPU 工作机：3 × 5060 Ti 16 GB、1 × 5070 Ti 16 GB），另有一台 Mac Hub。
   按 [部署指南](../guides/deployment.md) 的「多机媒体工作流部署」把主控、工作机和 Hub 配好；#299 清单通过后再做本清单。
2. 更新后 4 台工作机都会显示 待核验，此时**一部片都不接**（1080p 也不接，影片在 待处理 里显示「未核验」）。
   在 设备 页对每台工作机点一次 **核验并启用** 后，16 GB 工作机才会同时接 1080p 和 4K（见下方第 5 项）。
3. 备好测试影片：一部约 40 GB 的源文件、几部 1080p 短片、至少两部 4K 短片。用不重要的片和测试用的 NAS 演员目录。
4. 备好电源/功率读数的方法（智能插座、功率计，或工作机自己的功耗页）和一把能直接拔网线的手。
5. 任何手动启动服务器的检查都要先设 `FILMPAW_DB` 指向临时文件，不要碰真实的 Filmpaw 库。

## 逐项确认

| # | 步骤 | 期望 | 结果 |
|---|---|---|---|
| 1 | 5G 网口：把约 40 GB 的源文件派给一台工作机，看传输阶段耗时 | 约 35–70 s 传完（5G 理论约 64 s，10G 更快）；传输结束后做哈希校验并通过；进度条可见 | |
| 2 | 10G 网口：同一份 40 GB 源文件再传一次（或换到 10G 的工作机） | 耗时接近 5G 时的一半或更短；哈希校验通过；吞吐能看出网口差别 | |
| 3 | 传输到一半拔掉工作机网线，等 30 秒再插回 | 传输从断点续传，不从头开始；完成后哈希校验通过；不出现重复文件或残留的半截暂存文件 | |
| 4 | 五台机器同时跑一批混合影片（至少 4 部 4K + 若干部 1080p），派单选 自动 | 先确认：更新后、核验前所有工作机都是 待核验、不接任何影片，影片显示「未核验」。逐台 核验并启用 后，16 GB 工作机同时接 1080p 和 4K；自动 选预计最早完成的机器；没有影片被派到 8 GB 的主控做修复 | |
| 5 | 在 设备 页对每台已核验的 16 GB 工作机，确认 4K 再核验的流程 | 更新后该工作机显示 待核验；点 核验并启用 后可接 4K；「显存不足 4K」只出现在真正不能接 4K 的机器上 | |
| 6 | 一部 4K 影片在 16 GB 工作机上修复，看 媒体处理 监控与影片详情 | 监控里能看到完整的 LTX 细节（4K 档位、LTX 设置、阶段进度）；修复完成并回传；影片详情里记录了该片的档位为 4K | |
| 7 | 修复进行中，在工作机上强行结束 Jasna（任务管理器结束进程，或模拟崩溃） | Job 杀掉整个进程树；任务管理器里没有残留的 Jasna 或子进程；该片回到 待处理，或显示错误原因，可重试；不丢失、不重复入库 | |
| 8 | 每台工作机各跑一部同分辨率影片，对照功率读数 | 实测功率与功耗页的估算在同一量级；记录每台 5060 Ti / 5070 Ti 的实测功率与 预计 的偏差（用来校准估算，不通过也不阻塞） | |
| 9 | 修复进行中拔掉一台工作机的网线（或关机） | 该片显示 设备失联，设备页显示 失联 N 分钟 且「后台重连中」；**不会自动改派**；其他影片照常处理 | |
| 10 | 对第 9 项的失联影片：先试 改派，再试 判定已停止 | 已开始处理的片，改派 被拒绝并提示「已开始处理，需先判定已停止」；失联满 5 分钟后 判定已停止 可用，确认后该阶段按取消计（免费重试）、影片重新派单；工作机恢复后交回的结果被丢弃。对一部**尚未开始**的失联派单，改派 可以直接改到另一台或 自动 | |
| 11 | 恢复第 9 项被拔网线的工作机 | 心跳恢复，设备页回到 在线；失联期间没有重复处理或重复入库 | |
| 12 | 在主控（5060 8 GB）上跑 ASR，源文件分别用 1080p 和 **4K** 各一部 | 两种都能识别并出字幕；4K 源文件在 8 GB 显存下不报显存不足（OD7 的延后项，在这里验证）；耗时记录下来 | |
| 13 | 对一部正在工作机上跑的影片点 停止并重新排队，确认停止 | 工作机在下次心跳停止任务并杀掉进程树；影片回到 待处理，不计入失败；之后可被再次派单 | |
| 14 | CX14：在 Mac Hub 上改 轮询间隔，点 立即重启，**重启进行中**退出应用（Cmd-Q） | 退出后没有残留的 `taskpaw-backend` 进程；`ps -o pid,pgid,command` 里旧后端进程组已空；再次启动能正常绑定端口 | |
