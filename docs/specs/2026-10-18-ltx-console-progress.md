# Jasna LTX console progress — issue #269

## Spec review and frozen contract

The operator approved `design-system/taskpaw-v3/preview/ltx-progress-v1.html`
and requested AFK implementation with Codex leading and Kimi K3 as the sole
external reviewer. This follows the Jasna 0.11.2 configuration work in #267.
The earlier patch-release and Desktop installer delivery instruction remains
applicable; the next version is 3.9.17. Installing or restarting live services
is not part of delivery.

The problem is missing and misleading LTX progress information: the existing
parser drops counters, elapsed time, stage ETA and rates other than frame/s.
The UI must reproduce the console's current observation without inventing
film or queue completion.

Acceptance criteria:

1. Both Agent and Hub task detail use the approved card: file, four compact
   stage indicators, original stage name with translation, stage number,
   percentage/bar, current/total count, rate, stage elapsed, stage remaining,
   and a separately labelled current LTX run remaining estimate.
2. Preserve reported decimal precision and rate units, including `frame/s`,
   `s/frame`, `s/step`, `step/s`, `it/s` and `s/it`. No conversion to fps.
3. Collapsible, selectable/copyable original progress text is plain text,
   bounded, and stripped of terminal control sequences. Missing data is `—`;
   a missing percentage makes the bar indeterminate. Unknown stage names
   remain visible with their original label and recognized values.
4. Each observed LTX update replaces its stage snapshot. Stage, speed-test,
   segment and file changes cannot inherit missing values from older updates.
   Task stop/failure/restart and LTX-to-BasicVSR++ changes remove live LTX data.
   Unrelated log messages do not manufacture progress. Silent upstream work
   cannot be detected from stdout; present values as the last console update.
5. Stage 100% is not film 100%. Do not average four stages into overall
   progress or pass a current LTX run ETA into the whole-film subtitle pipeline.
   Existing actual queue/subtitle progress remains independently visible.
6. Handle CR/LF, ANSI sequences, UTF-8 split across reads and an EOF without
   newline. Keep existing hidden captured LTX process ownership and poll API.
7. Use recorded real console fixtures plus output generated by the actual
   v0.11.2 progress formatter. Cover missing/unknown fields, all four stages,
   speed test, repeated stages, mixed models, lifecycle and Agent/Hub rendering.
   Compare a real LTX console trace with the rendered production component;
   distinguish recorded/replayed evidence from a new GPU inference run.
8. Keep 375px layouts usable, keyboard-operated disclosure/copy controls,
   accessible progress names, reduced-motion behavior and both UI languages.

Allowed behavior changes are confined to LTX telemetry parsing, the status
fields that expose it, the shared progress component, and its tests/docs.
No presets, inference parameters, model download, task launch authorization,
poll/event protocol rewrite, V2 feature changes or live deployment.

## Verified upstream behavior and assumptions

Source: Jasna tag `v0.11.2`, `jasna/ltx/restore.py`, class `Progress` and
`_StageBar`; `restore_spans` runs a speed test when a speed profile is absent.
Immutable source: [restore.py at b623466](https://github.com/Kruk2/jasna/blob/b623466f6b479ab88790b25e17a2c84456367eda/jasna/ltx/restore.py).
The formatter uses tqdm with descriptions `LTX N/4 NAME` and
`LTX speed test N/4 NAME`; counters and time/rate text are tqdm output.
`run … left` estimates the remaining passes of that Progress instance. It
must not be labelled the whole file, output mux, subtitle job or queue ETA.
`begin(stage)` reports a callback before model loading but does not itself
print a console progress line; the captured CLI cannot identify that silent
transition. No guessed stage/timer transition will be added.
Segmented spans are aggregated into one run/bar per pass. With no mosaic
windows, scan can jump to compose; stage indicators show position, not proof
that every earlier stage performed work. `LTX plan` log messages are not stage
transition signals.

Existing recorded 0.11.1 samples live in `taskpaw_v3/tests/test_jasna.py`.
The approved HTML contains explicitly simulated examples; its fabricated
file/device/queue values and scenario controls are not production data.
Recorded CR-delimited real output sometimes appends a warning after the
closing tqdm `]` on the same line. `raw_line` ends at that closing bracket;
unrelated warning text is not copied into the progress payload. Initial tqdm
unknowns include `?frame/s`, `?step/s` and `?` ETA; these stay unknown.
GPU performance and a fresh v0.11.2 inference run remain unverified until
safe runtime evidence is available. Recorded trace replay validates display
and transport, not performance or installation on every GPU.

## Approach and shared data contract

Add optional `metrics.ltx_progress`, a JSON object, without changing the
existing status envelope. A recognized progress header supplies:

| Field | Type | Meaning |
|---|---|---|
| `mode` | `"restore"` or `"speed_test"` | The observed console prefix |
| `stage_index`, `stage_total` | positive integer | Original stage position; index cannot exceed total |
| `stage_name` | string | Original bounded name, including unknown names |
| `percent` | optional finite number in 0–100 | Stage bar value |
| `percent_text` | optional string | Original numeric percentage spelling |
| `current`, `total` | optional string | Original tqdm counter tokens, not global frames |
| `rate_value`, `rate_unit` | optional string | Original numeric spelling and unit |
| `elapsed`, `eta`, `run_eta` | optional string | Stage elapsed, stage left and current LTX run left |
| `raw_line` | string | Latest accepted console progress line, controls removed, at most 4096 characters |

Optional fields are absent when not supplied/recognized, never carried forward
from another snapshot. A rate is shown only when both its value and unit are
valid. Known stages infer a count label (`scan`, `encode`, `compose`: frames;
`denoise`: steps); unknown stages use a neutral count label.

Retain `ltx_stage`, top-level stage `percent`, and compatibility `fps` only for
reported frame/s; `eta` can remain the reported LTX run ETA for older viewers.
Modern UI prefers the complete structured snapshot and never fills its missing
fields from the legacy fields. Older Agents' `ltx_stage` data still renders,
with missing new fields unknown. Legacy compatibility does not make the
top-level ETA a whole-film estimate: suppress it in both backend subtitle
progress and the frontend pipeline whenever LTX is active.

The parser clears LTX and stage-scoped legacy values before admitting a
subsequent ordinary progress observation. The existing monitor lifecycle
resets progress at launch and emits live progress only during running restore;
tests must verify stop/failure/restart, not just the pure parser. A marker of
an upstream new LTX pass/segment may reset the snapshot only when verified in
source or a real trace. No time-based assumption about a stage change.

`MonitorMetrics` detects any valid structured/legacy LTX stage, hides its raw
metric keys, and renders one shared `LtxProgress` component. Known four-stage
orders get the stepper; unknown orders get their literal stage header without
claiming which other stages completed. Use current theme tokens and MUI.
The console disclosure defaults collapsed, copy has success/failure feedback,
and the latest text remains selectable if clipboard access is unavailable.

## Risks and test plan

- Parsing tqdm strings can lose unknown formats: retain the latest bounded raw
  progress line; test real fixtures, original formatter output, unknown stages,
  decimal rates and partial snapshots. Preserve reported inconsistency instead
  of recomputing a plausible ETA.
- Nested metrics travel through existing JSON status: test serialization and
  shared Hub rendering, while retaining old-Agent compatibility.
- Stale values could mislead long-running mixed batches: test fresh snapshot
  replacement, restart, LTX/ordinary switches, EOF/CR/ANSI input and failure.
- Scope leakage into the subtitle pipeline: test stage 100% and run ETA never
  become whole-film figures; existing queue values remain unchanged.
- Clipboard may be unavailable in a browser/Hub: catch the failure, show clear
  feedback and keep selectable raw text. Test it without adding a dependency.
- Verify production component screenshots at desktop and 375px, all scenarios,
  keyboard disclosure, reduced motion and missing values. Demo-only controls
  and hardware values never enter the shipped task view.

Implement failing behavioral tests first, then parser and UI changes, focused
checks, internal review, sole Kimi K3 review, full native checks and remote CI.
Record any environmental baseline failures separately from passes; never call
a partially failing suite green. No merge while required checks or an admitted
in-scope finding remain unresolved.
