# 阶段 1 待实机清单（交给操作者 / T09）

阶段 1 的全部代码都只在临时目录、模拟 NAS 与假工具上验证过。下面这些只有在你的真实环境里才能确认。
建议先用一部不重要的短片、一个测试用的 NAS 演员目录。

## 准备

1. 装好包含阶段 1 的 Taskpaw 与 Filmpaw 构建（集成 PR 合并或本地构建后）。
2. Taskpaw `agent.yaml` 的 `workflow:` 段：`enabled: true`、`inbox_root`（本机收件目录）、`ffprobe_path`、
   `jasna_exe_path`、`whisperjav_exe_path`、`mdcx_python` / `mdcx_root` / `mdcx_profile`（Miko 的 python、
   MDCX304 目录、你的 Miko config.json）；Filmpaw 用默认库目录时 `filmpaw_data_dir` 留空。
3. 先打开 Filmpaw（它启动后会在库目录写 `workflow-endpoint.json`），再启动 Taskpaw。

## 逐项确认

| # | 操作 | 期望 |
|---|---|---|
| 1 | 往 INBOX 放一部短片（单卷，带日文字幕或不带） | 「媒体入库」页出现该片，依次走 修复 → 识别 → 翻译 → 回传 → 整理（Miko） |
| 2 | 5060 上的 LTX 修复与 WhisperJAV 识别 | 不与手动 Jasna/字幕任务抢 GPU；进度可见；中途关闭 Taskpaw 再开，阶段被正确结算或重试 |
| 3 | Miko 整理完成后打开详情抽屉 | 封面、标题、演员、分卷文件、中文字幕标识与你平时 Miko 手动整理一致 |
| 4 | 搜索并选择 NAS 演员目录，点「确认入库」 | NAS 上该演员目录下出现新的影片目录，文件齐全；没有覆盖任何已有内容 |
| 5 | 入库完成后 | INBOX 里该片的原文件与空目录被删除；Taskpaw 工作目录里该片的临时文件被回收 |
| 6 | 归档进行中关闭 Filmpaw，再打开 | 归档按操作键核对，结果只复制一次；不出现第二个目录 |
| 7 | 让 NAS 断网 / 休眠时确认入库 | 显示「等待 Filmpaw / NAS」，恢复后继续；不报错丢失 |
| 8 | NAS 空间不足或无写权限 | 归档失败并显示原因；可处理后重新确认 |
| 9 | 入库前把 INBOX 原片换成另一个同名文件 | 该文件被保留并显示「待清理（来源已变化）」，其余正常清理 |
| 10 | 多卷影片（cd1/cd2） | 两卷进同一影片目录，folder.jpg 正确；若各卷字幕/4K 不同，见下方待决定事项 |

## 需要你决定的事项

- **多卷标识不一致**（M01 IR01/CX-M2）：各卷中文字幕或 4K 不一致时，Miko 会按标识把各卷分到不同目录，当前处理为
  「需处理」。可选：强制关闭 Miko 的「目录名加字幕标识」(`folder_cnword`)，代价是所有影片的目录名不再带 -C。
- **NTFS 备用数据流竞态**（F02 Codex r3）：清理哈希的几秒内若有其他程序给 INBOX 原片写入备用数据流，可能一并删除；
  已存在的备用流会被拒绝删除。家用下判断为不可达（P2 延后）；如需修复请告诉我。
- **已归档但 NAS 离线导致核对失败**（F02 IR05）：极少见；若出现「需复核」，到 NAS 上确认目录完整后手动处理。
